# OpenDMA User Guide

This guide describes how to integrate and operate `odma_core` in phase a, Direct Register Mode (DR mode). The
register map, the register fields and the programming sequences are those of \[PG021\] (AMD AXI DMA product guide,
version 7.1); this guide states where OpenDMA implements, interprets or omits a part of it. The register map with all
fields is [hdl/odma_registers/docs/register_map.md](../hdl/odma_registers/docs/register_map.md), the C header
`sw/odma_regs.h`.

## 1. Sources

The synthesis sources are listed in `compile_order.txt` (generated by `python run.py --compile-order`) in compile
order. The Open Logic sources go into the VHDL library `olo`, the OpenDMA sources into the library `opendma`; the
top level is `opendma.odma_core`. Open Logic is the submodule `open-logic/` (open-space-hdl/open-logic-ft, tag
4.7.0-ft.6). All sources are VHDL-2008.

## 2. Generics

| Generic | \[PG021\] parameter | Range in phase a | Default |
| --- | --- | --- | --- |
| `IncludeSg_g` | `c_include_sg` | false | false |
| `IncludeMm2s_g`, `IncludeS2mm_g` | `c_include_mm2s`, `c_include_s2mm` | boolean, at least one true | true |
| `LengthWidth_g` | `c_sg_length_width` | 8 to 26 | 14 |
| `AddrWidth_g` | `c_addr_width` | 32 to 64 | 32 |
| `Mm2sMemWidth_g`, `S2mmMemWidth_g` | `c_m_axi_mm2s_data_width`, `c_m_axi_s2mm_data_width` | 32, 64, 128, 256, 512, 1024 | 32 |
| `Mm2sStreamWidth_g`, `S2mmStreamWidth_g` | `c_m_axis_mm2s_tdata_width`, `c_s_axis_s2mm_tdata_width` | 8, 16, ..., 1024, at most the memory width | 32 |
| `Mm2sBurstBeats_g`, `S2mmBurstBeats_g` | `c_mm2s_burst_size`, `c_s2mm_burst_size` | 2, 4, ..., 256 | 16 |
| `StsCntrlStrm_g`, `UseRxLength_g` | `c_sg_include_stscntrl_strm`, `c_sg_use_stsapp_length` | false | false |
| `MicroDma_g` | `c_micro_dma` | false | false |
| `Mm2sBufferBeats_g`, `S2mmBufferBeats_g` | none: depth of the data buffer of a channel in stream beats | at least two bursts (2 x burst x memory width / stream width) | 64 |
| `ExtRegs_g` | none: extension register window 0x100 to 0x1FF | boolean | true |

An inconsistent configuration stops the elaboration with a message that names the generic. The defaults of
`IncludeSg_g` and `StsCntrlStrm_g` differ from \[PG021\] (architecture section 6): a configuration taken from a
system with the vendor core sets them explicitly. Bursts never cross 4 KB, so a channel with a wide memory issues
bursts of at most 4096 bytes whatever the burst generic is (32 beats of 1024 bits). The verification report of
`odma_core` lists the simulated and the synthesised values of every generic.

## 3. Clock and reset

All ports belong to `Clk`, the synchronous configuration of \[PG021\]; the core has no clock domain crossing. A
system with other stream or memory clocks places `olo_ft_fifo_async` (with `SyncTmr_g` = true) at the ports. `Rst`
is synchronous and high-active and resets the whole core. A soft reset (section 5.4) resets the channels and the
registers but not the AXI4-Lite slave, so that the register access that starts it completes.

## 4. Interfaces

| Interface | Ports | Content |
| --- | --- | --- |
| Register port | `S_AxiLite_*` | AXI4-Lite slave, 10 address bits, 32 data bits. Every access gets OKAY; a write uses all 32 bits whatever `WStrb` holds; offsets without a register read 0 |
| MM2S memory port | `M_AxiMm2s_Ar*`, `M_AxiMm2s_R*` | AXI4 read master: INCR bursts of full-width beats, `ArCache` 0011, `ArProt` 000, no ID signals; up to 8 bursts outstanding |
| MM2S stream | `M_Mm2s_Data`, `_Keep`, `_Last`, `_Valid`, `_Ready` | AXI4-Stream master: one packet per transfer, first byte in lane 0, `TKeep` contiguous from lane 0 in the last beat |
| S2MM stream | `S_S2mm_Data`, `_Keep`, `_Last`, `_Valid`, `_Ready` | AXI4-Stream slave: packets of any length; the bytes of the last beat are those up to the first lane whose `TKeep` bit is clear; `TKeep` of the other beats is not used |
| S2MM memory port | `M_AxiS2mm_Aw*`, `M_AxiS2mm_W*`, `M_AxiS2mm_B*` | AXI4 write master: INCR bursts with write strobes, `AwCache` 0011, `AwProt` 000, no ID signals; a burst is requested only when all its data is in the core |
| Interrupts | `Mm2s_Irq`, `S2mm_Irq` | Level, high-active: the OR of the enabled `IOC_Irq` and `Err_Irq` flags of the channel |
| ECC interrupt | `Ecc_Irq` | Level, high-active: an enabled flag of `ECC_STATUS` (extension window) |
| Reset outputs | `Mm2s_RstOut`, `S2mm_RstOut` | High-active, during `Rst` and during a soft reset: reset of the stream peers |

The ports of a channel that the configuration does not include keep constant idle values (valid and ready outputs
'0', burst type INCR, cache 0011, all other outputs 0), and its inputs may stay open.

## 5. Programming sequence

### 5.1 MM2S transfer

1. Write `MM2S_DMACR` with `RS` = 1 and, for completion by interrupt, `IOC_IrqEn` and `Err_IrqEn`.
2. Poll `MM2S_DMASR` until `Halted` reads 0.
3. Write the buffer address to `MM2S_SA`, with more than 32 address bits also the upper part to `MM2S_SA_MSB`.
4. Write the length in bytes to `MM2S_LENGTH`; this write starts the transfer.
5. Wait for `Mm2s_Irq` or poll until `MM2S_DMASR.Idle` reads 1.
6. Clear `IOC_Irq` by writing 1 to it in `MM2S_DMASR`.

The buffer is sent as one packet. Steps 3 to 6 repeat for every transfer while the channel runs.

### 5.2 S2MM transfer

The same steps with `S2MM_DMACR`, `S2MM_DMASR`, `S2MM_DA`, `S2MM_DA_MSB` and `S2MM_LENGTH`; the length is the size
of the buffer. After the completion `S2MM_LENGTH` reads the number of bytes of the received packet. The channel takes
stream data only while it runs; a packet that arrives before its transfer is programmed waits in the data buffer.

### 5.3 Halt

Writing `RS` = 0 halts a channel; `DMASR.Halted` reads 1 once it has stopped. A transfer in progress is completed:
MM2S sends it to its end; S2MM writes the chunks of the packet that are complete in its buffer, discards the rest of
the packet up to its `TLast` and does not report the completion (interpretation I8 of `odma_registers`). A following
start resumes the channel with the next programmed transfer.

### 5.4 Errors and soft reset

An error halts its channel: `DMASR` shows the error flag and `Err_Irq`, `DMACR.RS` reads 0, and `DMASR.Halted`
follows when the channel has shut down, a few clock cycles after the interrupt. After an error, software waits for
`Halted`, reads the flags and resets the core: it writes `DMACR.Reset` = 1 of either channel and polls until `Reset`
reads 0. The other channel keeps working until the reset.

| Error | Flags |
| --- | --- |
| Read response SLVERR (MM2S); the packet is still sent completely | `MM2S_DMASR.DMASlvErr` |
| Write response SLVERR (S2MM); no further write for the packet, the rest of the packet is discarded up to `TLast` | `S2MM_DMASR.DMASlvErr` and `DMAIntErr` |
| Buffer beyond the top of the address space: no memory access, no stream data | `DMADecErr` (S2MM also `DMAIntErr`) |
| S2MM packet longer than the buffer: the bytes that fit are written, nothing beyond the buffer, the rest discarded up to `TLast` | `S2MM_DMASR.DMAIntErr` |

The soft reset resets both channels. It stops them at once, completes every AXI transaction the memory has accepted
(read data is discarded, write data of accepted bursts is written), takes no S2MM stream data and holds both reset
outputs high; the stream peers connected to them abandon their packets. Then the registers return to their reset
values, and an error injection pending in an FT buffer is cancelled.

### 5.5 Extension window

With `ExtRegs_g` the offsets 0x100 to 0x1FF hold an identification word (`EXT_ID` = 0x4F444D41), the version, the
values of all generics, the ECC counters of the FT buffers, their flags with the enables of `Ecc_Irq` and an error
injection (register map). The FT buffer indices are 0 MM2S read data, 1 S2MM data, 2 S2MM chunk, 3 S2MM write
data, 4 MM2S transfer and 5 MM2S response; the other indices count nothing in phase a. Software written for
\[PG021\] does not access the window.

## 6. Protection scope

The core is designed for radiation environments together with the triple modular redundancy (TMR) of the synthesis
tool, like the Open Logic ft entities it is built on. It protects the parts in the first rows itself and relies on
TMR for all other logic:

| Part | Protection | Indication and test |
| --- | --- | --- |
| The six FT buffers: MM2S read data, transfer and response buffers; S2MM data, chunk and write data buffers | SECDED ECC of the Open Logic ft entities: a single error is corrected, a double error is detected and counted; the data of a double error is passed on as read, and the transfer result is not changed | `ECC_COUNT_0` to `ECC_COUNT_5`, `ECC_STATUS`, `Ecc_Irq` with `ECC_ENABLE`; error injection through `ECC_INJECT` |
| Clock domain crossings and reset synchronisers | The core has none (one clock domain); an `olo_ft_fifo_async` placed at a port by the integrator uses triplicated synchronisers (`SyncTmr_g` = true) | none |
| State machines | Recovery state through the `when others` branch and the reset | none |
| All other logic: registers of the control and data paths, counters, pointers, pipeline registers | TMR of the synthesis tool (for example `syn_radhardlevel` = `tmr` with Synplify, or the equivalent setting of the tool chain). The core adds no protection of its own for this logic; without TMR, an upset in it is not covered | synthesis report |

The integrator:

- enables the TMR of the synthesis tool for the core and the logic around it,
- checks in the synthesis report that TMR was applied, that the synchroniser chains of the crossings were not
  triplicated a second time, and that no register-based storage meant to be protected by TMR was inferred as a RAM
  primitive,
- requests safe state machines, so that synthesis keeps the `when others` branches (AMD Vivado: property
  `FSM_SAFE_STATE` = `default_state` on the state registers; Synplify: attribute `syn_encoding` = `safe`),
- protects the configuration memory of SRAM-based FPGAs by scrubbing; this is part of the FPGA design, not of the
  core.

The ECC paths are verified in simulation by error injection. Whether the protection as a whole meets the
requirements of a mission is shown by a radiation test with the core in operation (TRL 5).

## 7. Performance

MM2S sends one stream beat per clock cycle when a burst has at least 8 stream beats (burst beats x memory width /
stream width) and the memory and the stream peer are ready; with fewer, the read latency of the memory is not hidden.
S2MM issues one write command per chunk of one burst, and the write master accepts the next command about 7 clock
cycles after the data of the previous one. With equal memory and stream widths a chunk of C stream beats therefore
takes about C + 7 clock cycles; with a memory at least four times as wide as the stream the channel takes one beat
per clock cycle. Measured with an always ready memory and a stream without gaps (verification reports of the
channels):

| Memory / stream width, burst beats | MM2S beats per clock cycle | S2MM beats per clock cycle |
| --- | --- | --- |
| 32 / 32 bits, 16 beats (the defaults) | 1.0 | 0.76 |
| 128 / 64 bits, 32 beats | 1.0 | 0.95 |
| 256 / 128 bits, 4 beats | 1.0 | 0.51 |
| 512 / 256 bits, 8 beats | 1.0 | 0.70 |
| 512 / 512 bits, 2 beats | 0.51 | 0.24 |
| Memory four or more times the stream width | 1.0 | 1.0 |

Short bursts at equal widths cost the most: a system that needs the full S2MM rate with equal widths chooses long
bursts (`S2mmBurstBeats_g` 64 or more gives at least 0.9 beats per clock cycle) or a wider memory port. A transfer
takes at least four clock cycles in the AXI master for its command, and the register accesses of DR mode add the
time of the processor for every transfer.

## 8. Integration constraints

| Constraint | Reason |
| --- | --- |
| TMR of the synthesis tool enabled for the core | The core protects its FT buffers itself and relies on TMR for all other logic (section 6) |
| The memory answers every burst in order (no ID signals) | The masters use one ID for all transactions |
| The stream peers are reset by `Mm2s_RstOut` and `S2mm_RstOut` | A soft reset ends the packets in progress; a peer that continues a packet sends its rest as a new packet |
| One clock for all ports | Synchronous configuration; asynchronous stream or memory clocks need FIFOs at the ports (section 3) |
| Phase a: `IncludeSg_g`, `StsCntrlStrm_g`, `UseRxLength_g` and `MicroDma_g` false | Scatter/Gather Mode, the control and status streams and the micro DMA follow in phases b and c |

## 9. Conformance

Implemented in phase a (\[PG021\] references in the compliance matrix, [docs/compliance.md](compliance.md)):

- Register map and fields of DR mode, the programming sequences of DR mode for both channels, the halt, the soft
  reset, the interrupt outputs and their enables, the reset outputs.
- Transfers at any byte address and of any length up to 2**`LengthWidth_g` - 1 bytes in every width configuration
  (the function of the data realignment engine, also for streams wider than 512 bits), 4 KB and burst splitting.
- The configuration generics of Table 44 listed in section 2, with the ranges of \[PG021\].

Partly implemented:

- `DMADecErr` for a DECERR response of the memory: Open Logic 4.7.0-ft.6 reports a failed AXI command without its
  response code, so a DECERR response sets `DMASlvErr` (S2MM with `DMAIntErr`) instead of `DMADecErr`. A buffer
  beyond the top of the address space sets `DMADecErr`. The distinction follows with the Open Logic release that
  reports the response code.

Not implemented in phase a: Scatter/Gather Mode, cyclic mode, interrupt coalescing and delay, keyhole transfers
(phase b); control and status streams, the receive length in the status stream, micro DMA (phase c). Not in scope:
multichannel mode and the asynchronous clock configuration.

## 10. Verification and tools

Each module has a specification, an architecture, a verification plan and a verification report in
`hdl/<module>/docs/`. The core tests (`odma_core`) execute the programming sequences of a model written from
\[PG021\] against the assembled core in seven configurations. `python run.py` runs the full regression with GHDL,
`python lint/synth_check.py` the synthesis check of the generics, `python tools/compliance.py --check` the
traceability to \[PG021\]. The technology readiness level is stated in the README and the roadmap.
